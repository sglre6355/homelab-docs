# Incident Report: 100G Nodes Lost Network Connectivity After Reboot

**Date:** 2026-07-04

**Cluster:** 3-node Proxmox (Dell R440, R540, R640)

**Affected:** R440 + R640 (100G ConnectX-4 uplinks). R540 (10G Broadcom) unaffected.

**Status:** Resolved with permanent workaround.

---

## TL;DR

The Mellanox ConnectX-4 (mlx5) driver fails to program its hardware **unicast MAC RX filter**
correctly when the NIC is enslaved to a **VLAN-aware Linux bridge** (`bridge-vlan-aware yes`). The
NIC advertises hardware unicast filtering (`IFF_UNICAST_FLT`), so the kernel does not enable
promiscuous mode on the bridge port — and the NIC then silently drops all unicast frames addressed
to its own MAC. Broadcast/multicast still passes, link stays UP, everything *looks* healthy.

This is a **known, long-standing mlx5 bug** (reports since 2021), not a config error and not fixable
by config. It was exposed on our side by enabling `bridge-vlan-aware` on vmbr0 (change made before
the reboot, took effect at reboot).

**Fix:** force promiscuous mode on the physical bridge port.

---

## Symptoms

- After reboot, node cannot ping gateway, LAN hosts, or other cluster nodes.
- `ip a` / `ip -br link` shows interface UP, LOWER_UP. `ethtool` shows link detected, correct speed,
  FEC active.
- Bridge config correct, port enslaved and forwarding, routes correct.
- `ip neigh` shows gateway/neighbors as INCOMPLETE — ARP never resolves.
- **The tell:** connectivity works *while tcpdump is running* on the interface and dies when it
  stops. (tcpdump puts the NIC in promiscuous mode, bypassing the broken filter.)
- tcpdump shows own ARP requests going out and broadcast traffic (other hosts' ARP, STP BPDUs)
  coming in — but unicast replies only arrive in promisc mode.
- Intermittent-looking behavior possible (filter state occasionally lands in a working state after
  reprogramming events).

## What it is NOT (checked and eliminated)

- Not optics/fiber/FEC — link never drops (`ip monitor link` silent during outages)
- Not the switch (CCR2216) — port forwarding, STP fine, no log events
- Not interface renaming — names stable
- Not bridge/VLAN misconfig — `bridge -d vlan show` correct (1 PVID untagged + 40)
- Not the size of `bridge-vids` — shrinking 2-4094 → 40 did not fix it (the >512 VLAN table overflow
  warning is a symptom of the same broken offload block, not the cause)
- Not a fresh kernel regression specific to us — same bug reported on kernels from ~5.x to 6.8+

## Diagnostic procedure (if it happens again)

```bash
# 1. Confirm link is genuinely up
ip -br link
ethtool <iface> | grep -E "Speed|Link detected"

# 2. Confirm ARP failure
ip neigh show            # INCOMPLETE entries = frames dying at L2

# 3. The definitive test — does promisc fix it?
ip link set <iface> promisc on
ping -c 3 <gateway>       # works?
ip link set <iface> promisc off
ping -c 3 <gateway>       # fails again?
# If yes/no → hardware RX filter bug confirmed. Apply the fix below.

# 4. Supporting evidence in dmesg: port joins bridge with
#    "entered allmulticast mode" instead of "entered promiscuous mode"
dmesg | grep -iE "mlx5|<iface>"
```

## The fix (applied to both 100G nodes)

In `/etc/network/interfaces`:

```text
iface nic4 inet manual
        pre-up ethtool -K $IFACE rx-vlan-filter off
        post-up ip link set $IFACE promisc on

auto vmbr0
iface vmbr0 inet static
        address 10.10.30.11/24        # .1x per node
        gateway 10.10.30.1
        bridge-ports nic4
        bridge-stp off
        bridge-fd 0
        bridge-vlan-aware yes
        bridge-vids 40
```

Then `ifreload -a` (or reboot) and verify.

**Why two lines:**

- `promisc on` — disables the broken hardware **MAC** filter (the actual fix)
- `rx-vlan-filter off` — disables the hardware **VLAN** filter from the same buggy offload block, so
  tagged VLAN 40 traffic can never depend on it. Promiscuous mode does not guarantee bypassing the
  VLAN filter on all drivers; this makes the bridge do VLAN filtering in software (negligible cost).
  Defensive, not strictly required.

Keep `bridge-vids` as an explicit list (currently `40`), not `2-4094` — the mlx5 vport VLAN table
maxes out at 512 entries and logs warnings beyond that.

**Note:** bonded interfaces are implicitly set promisc by the bond driver, which is why bonded
Mellanox setups don't hit this. If these NICs are ever moved into a bond, the workaround becomes
redundant (but harmless).

## Alternatives considered (not adopted)

1. **NVIDIA out-of-tree mlnx_en driver** — reported to fix the bug properly, but requires
   maintaining DKMS builds against every Proxmox kernel update, and CX-4 support in new releases is
   ending (EOL hardware). Fragile.
2. **switchdev eswitch mode** — also reported to work, but changes VF behavior and creates extra
   vport interfaces. Overkill without SR-IOV needs.
3. **Non-VLAN-aware bridge** — works (implicitly promisc), but loses per-VM VLAN tagging on one
   bridge; would need separate vmbr per VLAN.

## Lessons learned

- `UP` in `ip a` ≠ working datapath; check ARP state and per-direction traffic first.
- "Works while tcpdump runs" = promiscuous mode is masking an RX filter problem. This is a
  diagnostic gift — test promisc deliberately, don't dismiss it as noise.
- Config changes staged before a reboot only take effect *at* the reboot; the reboot is the trigger,
  not the cause. Audit everything changed since the last boot.
- Both identical nodes failing simultaneously points to a shared factor (same NIC + same config
  change), not two independent hardware failures.
