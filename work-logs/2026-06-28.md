## VLAN30 (Server Network) over 100G QSFP28

VLAN30 (10.10.30.0/24) was already created on the CCR2216 (SVI/gateway 10.10.30.1, bridge VLAN
table). The remaining work was attaching the servers' 100G QSFP28 links.

All three nodes have a Mellanox ConnectX-4, but the CCR2216 has only **2x QSFP28 ports**, so the
100GbE links go to two nodes and the third runs 10GbE:

- R440 -> `qsfp28-1-1` (100GbE)
- R640 -> `qsfp28-2-1` (100GbE)
- R540 -> SFP+ 10GbE on VLAN30

(Earlier in this session R540 was brought up on `qsfp28-2-1` at 100G for the iperf test below, then
moved to a 10GbE SFP+ link so R640 could take the second QSFP28 port.)

### CCR2216 port configuration

Each QSFP28 port is an untagged VLAN30 access port; the bridge is tagged for the SVI.

```routeros
# add the port to the bridge with PVID 30
/interface bridge port add bridge=bridge interface=qsfp28-1-1 pvid=30
/interface bridge port add bridge=bridge interface=qsfp28-2-1 pvid=30

# VLAN30 untagged member list (full-replace list, include both ports)
/interface bridge vlan set [find vlan-ids=30] untagged=qsfp28-1-1,qsfp28-2-1
```

R540's 10GbE SFP+ link lands on `sfp28-1` and joins VLAN30 as an untagged access port (same
pattern):

```routeros
/interface bridge port add bridge=bridge interface=sfp28-1 pvid=30
# append to the VLAN30 untagged list alongside the two QSFP28 ports
/interface bridge vlan set [find vlan-ids=30] untagged=qsfp28-1-1,qsfp28-2-1,sfp28-1
```

### Mellanox card: InfiniBand -> Ethernet mode

The MCX455A is a VPI card and at least one card was in InfiniBand mode, which never links to the
CCR's Ethernet QSFP28. Switch the port to Ethernet with `mlxconfig`:

```sh
mst start
mlxconfig -d <pci-id> query | grep -i link_type
mlxconfig -d <pci-id> set LINK_TYPE_P1=2   # 2 = Ethernet
# cold power-cycle the host afterwards
```

#### Transferring the mlxconfig binary via iDRAC Virtual Media

The host had no easy network/USB path to pull the MFT package, so the binary was carried in on a
FAT32 disk image mounted through the iDRAC Virtual Media connection. Build the image on a Linux
workstation:

```sh
IMG=image.img
truncate -s 1G "$IMG"                                  # size to taste
parted -s "$IMG" mklabel msdos                         # create the partition table first
parted -s "$IMG" mkpart primary fat32 1MiB 100%
LOOP=$(sudo losetup --find --show --partscan "$IMG")
sudo mkfs.vfat -F 32 "${LOOP}p1"
sudo mount "${LOOP}p1" /mnt
sudo cp file /mnt                                       # e.g. the mlxconfig / MFT package
sync
sudo umount /mnt
sudo losetup -d "$LOOP"
```

Then attach `image.img` in iDRAC -> Virtual Media and mount it inside the OS.

### Link would not come up: CWDM4 needs RS-FEC

After the VLAN config and Ethernet mode were correct, `qsfp28-1-1` still showed `status: no-link`
despite a healthy `sfp-rx-power` (~0.33 dBm, i.e. light was arriving fine).

Diagnosis (`/interface ethernet monitor qsfp28-1-1 once`):

- Optic = CIG **TRQ5E14ENF** — a 100G QSFP28 **CWDM4** module (1310nm, single-mode, 2km, LC duplex).
  RouterOS reports it under the generic `100G-baseSR4-LR4` label.
- Good RX power + no link points to a PCS-lock failure, not cabling.

Root cause: **FEC mismatch.** Unlike LR4 (10km, no FEC required), CWDM4 (2km) runs a higher pre-FEC
BER and relies on **RS-FEC (Clause 91 / `fec91`)** to be viable. RS-FEC changes the PCS transcoding,
so if the two ends disagree on FEC the lanes never align and the link stays down. `fec-mode=auto` on
the CCR did not settle on RS-FEC. (Auto-negotiation is a red herring here — there is no Clause 73
link autoneg on optical 100G.)

Fix — force RS-FEC on both ends:

```routeros
# CCR2216
/interface ethernet set qsfp28-1-1 fec-mode=fec91
/interface ethernet set qsfp28-2-1 fec-mode=fec91
```

```sh
# Proxmox host
ethtool --set-fec <iface> encoding rs
ip link set <iface> up
```

After this both links came up at 100Gbps (`/interface ethernet monitor` -> `link-ok`,
`rate: 100Gbps`).

## Proxmox installation and cluster

- Proxmox installed on all three nodes (R440, R540, R640).
- Each host's VLAN30 interface is a Linux bridge (`vmbr30`) over the Mellanox NIC with a static IP
  on 10.10.30.0/24 (gateway 10.10.30.1), parallel to the iDRAC scheme:
  - R440: 10.10.30.11
  - R540: 10.10.30.12
  - R640: 10.10.30.13
- Created cluster `sgr-pve-cluster` and joined all three nodes.

## PSU power-redundancy warning (all nodes)

iDRAC flagged a power-redundancy warning because PSU 2 had no AC supplied. Resolved by removing the
PSU 2 modules from all nodes and doing a complete cold boot (PSU 1 also disconnected from AC). On
restart the Lifecycle Controller re-ran CSIOR (Collect System Inventory On Restart), the system
recorded the non-redundant single-PSU configuration as the desired state, and the warning cleared.

## 100G throughput test (iperf3)

iperf3 between R440 and R540 over VLAN30, while R540 was still on `qsfp28-2-1` (hardware-switched
between the two QSFP28 ports at 100G):

- 4 parallel streams, 30s: **SUM 74.3 Gbits/sec** (259 GBytes, Retr 133).
- Per-core CPU is the limiting factor (single ConnectX-4, `iperf3` per-stream is single-core).

Not yet applied, available as headroom for a future max-throughput run:

- Jumbo frames (MTU 9000 end-to-end: Mellanox iface + `vmbr30` on both hosts, and raise the CCR
  QSFP28 ports' `l2mtu`).
- More streams across more cores (note Debian 12 / PVE 8 ships `iperf3` 3.12, which is
  single-threaded; `iperf3` >= 3.16 multithreads `-P`).
