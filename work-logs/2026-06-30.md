# Home Rack Setup Work Log 2026-06-30

## Aim

Decide the cluster storage strategy and stand it up, then build a dedicated network for VM/LXC
workloads.

## Storage Strategy Decision

Evaluated the options for `sgr-pve-cluster` storage:

- **Ceph (hyperconverged)** — true shared storage, self-healing, no single point of failure; wants
  3+ nodes and a uniform fast fabric.
- **ZFS local + Storage Replication** — simple, snapshots/compression, async replication for fast
  live migration; tolerates nodes being powered off.
- **NFS / iSCSI (single target)** — shared but reintroduces a single point of failure and (for
  iSCSI/thick-LVM) loses snapshots; needs a SAN/dedicated box we don't have.

Working constraints: live migration wanted, hard redundancy not required, and a desire to run only
~2 nodes day-to-day for electricity cost.

**Decision: Ceph.** Known trade-off recorded for later: Ceph prefers all three nodes up. With one
node powered off the cluster keeps serving (`min_size=2`) but stays degraded (`HEALTH_WARN`) since a
third replica can't be placed on two hosts; with two off, MON quorum is lost and Ceph stops. Also,
because Ceph writes are synchronous across hosts, R540's 10GbE uplink sits in the write path as the
slowest replica (unlike a local-ZFS design, where the 10GbE link would not matter).

## Ceph Cluster

- 3-node, one 466GB SSD OSD per host — the healthy minimum at the default `size=3 / min_size=2` (one
  replica per host).
- Ceph public/cluster traffic rides VLAN30 (the 100G QSFP28 fabric), same NIC as host mgmt and
  corosync (single ConnectX-4 per node).
- 3 MONs (one per node) for quorum.

Idle disks and their intended use:

- **R440 spare 466GB SSD** — a second OSD here would not grow usable capacity (the pool is capped by
  the smallest host, ~466GB usable), so it is kept as a cold spare. To actually expand the pool, add
  matching SSDs to R540 and R640 so all hosts grow uniformly.
- **R640 1863GB HDD** — a lone HDD on one host can't form a replicated Ceph pool, so it is reserved
  for local use (Proxmox Backup Server datastore / vzdump target / ISO store).

## VM Networking (VLAN40 Workload Network)

Each node link (`qsfp28-1-1` R440, `qsfp28-2-1` R640, `sfp28-1` R540) carries VLAN30 **untagged**
for host/Ceph/corosync. To keep workload traffic off the storage/cluster subnet, added a dedicated
**tagged** VLAN40 (`10.10.40.0/24`, gateway `10.10.40.1`) over the same trunk, so the host stays
untagged on VLAN30 while VMs/LXC ride tagged VLAN40.

### CCR2216

```routeros
# SVI / gateway
/interface vlan add name=vlan40 interface=bridge vlan-id=40
/ip address add address=10.10.40.1/24 interface=vlan40

# tag VLAN40 on the node links + bridge (ports stay untagged VLAN30 with pvid=30)
/interface bridge vlan add bridge=bridge vlan-ids=40 \
    tagged=bridge,qsfp28-1-1,qsfp28-2-1,sfp28-1 comment="VLAN40 Workload Network"

# DHCP
/ip pool add name=vlan40-pool ranges=10.10.40.100-10.10.40.200
/ip dhcp-server add name=dhcp-vlan40 interface=vlan40 address-pool=vlan40-pool lease-time=1d
/ip dhcp-server network add address=10.10.40.0/24 gateway=10.10.40.1 dns-server=1.1.1.1
```

Firewall: allow VLAN40 DHCP to the router (input) and VLAN40 -> WAN (forward); block VLAN40 from
reaching VLAN10/20/30 so workloads can't touch the management/iDRAC/storage networks. NAT is already
covered by the blanket masquerade on the WAN out-interface.

VLAN40 is intentionally **not** tagged toward `sfp28-11` (the x510 uplink) — no workloads live on
that side.

### Proxmox (per node)

Made `vmbr0` VLAN-aware so it can carry the untagged host IP (VLAN30) and tagged VM traffic (VLAN40)
on the one bridge:

```text
auto vmbr0
iface vmbr0 inet static
    address 10.10.30.1x/24
    gateway 10.10.30.1
    bridge-ports <mellanox-iface>
    bridge-stp off
    bridge-fd 0
    bridge-vlan-aware yes
    bridge-vids 2-4094
```

Because `vmbr0` carries Ceph + corosync + host mgmt, this was done
**one node at a time from the iDRAC console**, confirming `pvecm status` (quorate) and `ceph -s`
(`HEALTH_OK`, OSDs up/in) before moving to the next node.

### Verification

Attached a test VM with NIC on `vmbr0`, VLAN tag 40. Confirmed it pulled a `10.10.40.x` address,
reached the gateway (`10.10.40.1`) and the internet, and could **not** reach the iDRAC subnet
(`10.10.20.x`) — segmentation working.
